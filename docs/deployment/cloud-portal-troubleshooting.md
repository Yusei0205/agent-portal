# Cloud portal troubleshooting guide

Problems met while deploying the serverless Agent Portal (CloudFront + Lambda + DynamoDB + S3 + AppSync Events + AgentCore) and how each was fixed. Each entry has the **symptom**, the **cause** and the **fix**.

Quick reference: account `366019841051`, region `ap-southeast-1`, stack `AgentPortalCloud`, Kiro runtime stack `AgentPortalSpikeB`. On Windows git-bash prefix AWS CLI calls that contain `/aws/...` paths with `MSYS_NO_PATHCONV=1`.

## Deploy checklist

1. `npm run build:web` (the stack uploads `dist/web` and clears the CloudFront cache; it refuses to synth if `dist/web/index.html` is missing).
2. `cd infra && npx cdk deploy AgentPortalCloud -c budgetEmail=<email> -c kiroRuntimeArn=<arn> -c storageBucket=<bucket>`.
3. Runner (Kiro) changes only: build the image from the **repo root** (`docker buildx build --platform linux/arm64 -f kiro-runner/Dockerfile -t <ecr>/agent-portal/kiro-runner:<tag> --push .`), set `IMAGE_TAG` in `infra/lib/spike-b-stack.ts`, then `cdk deploy AgentPortalSpikeB`.
4. Docker Desktop must be running (the Lambda is a container image).

## Deploy and infrastructure

### CDK asset is 431 MB / "recursive asset" error
- **Cause:** the Docker build context included `infra/`, `cdk.out`, `node_modules`, data folders.
- **Fix:** `.dockerignore` excludes `infra`, `docs`, `data-*`, `**/node_modules`, `.playwright-mcp`; the image asset uses `ignoreMode: cdk.IgnoreMode.DOCKER`.

### Deploy fails: Docker daemon not running
- **Fix:** start Docker Desktop and redeploy.

### "Cannot perform more than one GSI creation or deletion in a single update"
- **Cause:** CloudFormation allows one index create/delete per table per update. We moved two indexes between tables in one deploy.
- **Fix:** change indexes one per table per deploy (two deploys). The failed stack rolls back cleanly (`UPDATE_ROLLBACK_COMPLETE`). New indexes show `CREATING` for a while while DynamoDB backfills; that is normal.

### Dashboard / project list fails for non-admin users: `AccessDeniedException ... dynamodb:Query on .../index/GSI-UserProjects`
- **Cause:** `infra/tables.json` (generated by `scripts/dump-dynamo-tables.ts`) put the projects repository's indexes on `portal-users`, but at runtime that repository uses `portal-projects`. The table had no indexes, so the role had no index permission and the query could not work. Admins skipped that code path, which hid it.
- **Fix:** the dump script now takes each repository's table from the `DYNAMODB_TABLE_PORTAL_*` name in its source file. Re-run `node --import tsx scripts/dump-dynamo-tables.ts` after adding or changing a repository's tables or indexes, and diff `infra/tables.json`.

### Web changes are not visible after deploy
- **Cause:** older stack versions did not upload web files at all.
- **Fix:** the stack now has a `BucketDeployment` (`WebFiles`). Always run `npm run build:web` first. Check what is live with `curl -s <portal-url>/ | grep -o "assets/main-[A-Z0-9]*.js"` and compare with `dist/web/assets`.

### Budget alerts
- A `$10` monthly budget (`agent-portal-10-usd`) emails the `budgetEmail` at 80% and 100%.

## CloudFront and the API

### POST requests return 403 (sign-in, saving settings, S3 test)
- **Cause:** CloudFront origin access control signs requests to a Lambda Function URL, but a POST with a body needs a payload hash the browser does not send.
- **Fix:** the Function URL is open (`authType: NONE`) and CloudFront adds a secret header (`x-portal-origin`). The server (`server/http.ts`) rejects requests without the secret (health check is exempt). Anyone calling the raw Function URL directly gets 403.

### API errors show up as the HTML page ("Cannot read properties of undefined (reading 'id')")
- **Cause:** a distribution-wide error response turned every 404 (including API 404s) into `index.html` with status 200, so the browser parsed HTML as JSON.
- **Fix:** no distribution-level error responses. A CloudFront Function (`SpaRewrite`) on the web (S3) behaviour only rewrites paths without a file extension to `/index.html`. API errors stay JSON.

### Jira (or any OAuth) says "redirect_uri is not registered" / sign-in link goes to the Lambda address
- **Cause:** links the server builds were based on the request's Host header, which behind CloudFront is the internal Lambda URL (and `http`).
- **Fix:** `server/public-url.ts` `publicBaseUrl(req)` uses `PORTAL_PUBLIC_URL` (deploy context `publicUrl`) and falls back to the request for local installs. Used for the Jira callback and invite links. Build any new server-side link the same way.
- **In Atlassian:** the app's callback URL must be exactly `<portal URL>/api/jira/callback`, e.g. `https://d1tah6dqw2fe9f.cloudfront.net/api/jira/callback`. Update it in the Atlassian developer console and in the project's Jira app settings.
- The Jira OAuth `state` is a signed value, not an in-memory entry, so the callback can land on any Lambda instance.

### Invite link "keeps loading"
Two separate causes:
1. **Wrong host:** the server built the link from the `Host` header, which behind CloudFront is the Function URL host (locked to CloudFront). The Users page now rebuilds the link on `window.location.origin`. Any other server-built link (OAuth callbacks, Google sign-in) has the same risk: use a configured public URL, not the request host.
2. **No page for the link:** the backend had `POST /api/auth/accept-invite` but the web app had no accept-invite screen, so the link only showed the sign-in form or a spinner. Added `AcceptInvite` (`web/src/pages/Auth.jsx`), shown by `App.jsx` when signed out and the hash starts with `#/accept-invite`. Test it in a private window, a signed-in admin session hides it.

## Lambda runtime behaviour

### "Could not reach the server" under light use
- **Cause:** the account's Lambda concurrency limit is 10 (Service Quota `L-B99A9384`). Every open SSE stream or long poll holds a Lambda slot.
- **Fix:** live updates use AppSync Events (WebSocket from the browser) instead of SSE (`server/realtime.ts`, `web/src/lib/realtime.js`), and long polls are short (about 6 s). Request a quota increase if you need more users.

### In-memory state is lost or per-instance
Lambda can run many instances, and an instance is **frozen** as soon as its response ends. Anything kept in memory (login state, the event bus) is invisible to other instances, and background work in a frozen instance does not progress. Store shared state in DynamoDB, and finish work before the response ends (`flushRealtime()` runs before each response so queued events are sent).

### Periodic jobs (idle session stop, attachment cleanup) do not run
- **Cause:** `setInterval` timers need a long-lived process. A Lambda instance is frozen between requests, so timers never fire reliably.
- **Fix:** EventBridge Scheduler schedules `agent-portal-idle-stop` (every minute) and `agent-portal-attachment-cleanup` (every 6 hours) invoke the Lambda with `{"job": "...", "secret": "..."}`. Lambda Web Adapter forwards that event as `POST /internal/events` (`AWS_LWA_PASS_THROUGH_PATH`), handled by `server/scheduled-jobs.ts`, which checks the secret (same value as the CloudFront `x-portal-origin` header) and runs the job from a whitelist. In-process timers are skipped when `AWS_LAMBDA_FUNCTION_NAME` is set.
- **Check it works:** `aws scheduler list-schedules --name-prefix agent-portal`; invoke by hand with `aws lambda invoke --payload fileb://event.json` (expect `{"ok":true,"job":"idle-stop"}`; a wrong secret gives 403). Add a new job by adding it to `JOBS` in `scheduled-jobs.ts` and to the `jobs` list in `infra/lib/portal-stack.ts`.
- **Not scheduled:** loop-spec `cron` triggers (nightly test fixer etc.) are stored but nothing executes them yet, on any backend.

### Scans and uploaded documents stay "processing" / "estimating" forever
- **Cause:** work started with `setImmediate(...)` after the HTTP reply never runs on Lambda, because the instance is frozen as soon as the reply ends.
- **Fix:** `server/background-jobs.ts`. Register a job with `registerBackgroundJob(name, fn)` and start it with `await runInBackground(name, args)` **before** sending the reply. On Lambda the portal then invokes itself asynchronously (`InvocationType: Event`, needs `lambda:InvokeFunction` on its own ARN, already granted); Lambda Web Adapter forwards the payload to `/internal/events`, which checks the secret and runs the job (up to 15 minutes). If the self-invoke fails the job runs inline. Locally it is a plain `setImmediate`. Jobs in use: `scan-estimate`, `scan-run` (resumable: use Resume if a scan hits the time limit), `knowledge-process`.
- Not converted: the tool-pack installer (`tool-packs.ts`), which installs local command-line tools and does not apply on Lambda.
- **Check:** invoke by hand: `aws lambda invoke --function-name agent-portal --payload fileb://event.json out.json` with `{"job":"scan-run","args":{"id":"x"},"secret":"<origin secret>"}` returns `{"ok":true,...}`.

### Agent-written files missing after a Claude or Kiro session
- The runners send back changed deliverable files (documents, images, spreadsheets, diagrams; up to 50 files, 10 MB each, 40 MB total) as chunked `file` events. The portal re-checks every path, extension and size (`server/agent/runner-files.ts`), writes them into the run's work folder and mirrors them to S3, and the normal end-of-run collection then lists them as output files. Other file types, tool folders (`.claude`, `.kiro`, `repos`, `node_modules`) and anything over the limits are skipped; the status line says how many were skipped.

### "Secret key must be a 64-character hex string"
- **Cause:** the master key secret was a random string, not hex.
- **Fix:** the CDK secret `MasterKeyHex` (`agent-portal/master-key-hex`) generates 64 hex characters. Changing the master key makes previously stored encrypted values (credentials, integrations) unreadable; re-enter them.

### "Project not found" / 403 on sessions, files, terminal, reviews (non-SQLite code paths)
- **Cause:** many modules still ran raw SQLite queries (`SELECT ... FROM projects / project_members`). In DynamoDB mode those return nothing.
- **Fix:** use the repositories. `server/project-access.ts` has `getProjectRow`, `getMemberRow`, `getProjectSlug`, `getMembership`, `getWorkflowRow`, `getLatestRunRow`, `getRepoRow` (plain-row results, same shape the old queries returned). All project and membership lookups now go through them (2026-11-03). Helpers are async: every caller must `await` (a missing `await` on an `async` access check is always truthy and silently lets requests through).
- **Still on local SQL, by design:** terminal and live browser (need an AgentCore shell or browser), the health ping, and the SQLite-only event insert in `agent/runner.ts`. Everything else the cloud portal uses goes through repositories. Check with `grep -rnE "\b(one|all)(<[^>]*>)?\(" server | grep -v repositories/`.
- **Browser test runs are not available on the cloud portal yet:** test runs start, then end with "Browser test runs are not available on the cloud portal yet". Everything around them (projects, scripts, groups, vault, case sets, script generation) works.
- **Tip:** the Lambda log does not record request paths. Reproduce with the browser Network tab and read the JSON error body.

## Kiro (AgentCore runner)

### Sign-in shows "code expired, close and try again"
- **Cause:** the login state was kept in an in-memory map, but the approval poll reached a different Lambda instance.
- **Fix:** login state is also saved in DynamoDB (`agentcore-login` repository) and `pollAgentCoreLoginShared` reads it.

### Sign-in done, status stays "pending" forever
- **Cause:** the result was only written by a background stream in the Lambda instance that started the login. That instance is frozen once its response ends, so it never recorded the approval.
- **Fix:** the runner keeps each login's outcome in memory and answers a new `kiro-login-status` request (even while the login is still running). The portal asks the runner directly (same AgentCore session id, derived from credential id + start time). Needs the runner image to include `kiro-login-status` (rebuild and redeploy `AgentPortalSpikeB` when the runner changes). A login started before that image was deployed cannot be recovered: sign in again.

### "Sign-in needed" or "created with outdated scopes" right after signing in
- **Cause:** the check required a `clientId`. A token from the AgentCore login has no `clientId` but does record `signedInAt`.
- **Fix:** treat a credential as valid when it has either (`server/credentials.ts`, `server/models.ts`).

### Model list shows only "Auto", or needs a manual Refresh
- **Cause 1:** the model list was a static value on Lambda (no `kiro-cli`). It is now fetched by the runner (`kiro-list-models` mode, `kiro-cli chat --list-models --format json`).
- **Cause 2:** the server cached the failed "no credentials" answer for 10 minutes. Failed or empty results are no longer cached and the New session dialog retries by itself (on tab focus, every 10 s, max 6 tries).

### AgentCore invocation returns 409 `RetryableConflictException`
- The runner handles one operation per session at a time. Status checks (`kiro-login-status`) are exempt; retry other calls.

## Testing module on DynamoDB

- Cases are stored under their case set and order, trace steps under their parent and sequence number, so editing or deleting them needs that context: `updateCase`/`deleteCase`/`getCaseById` take the case set id, `updateTraceStep` takes `{case_set_id|generation_id, seq}`. SQLite ignores the extra argument.
- Deleting a test project, group, case set or script removes its children explicitly (`server/testing/data.ts`, routes); SQLite does it by cascade, DynamoDB does not.
- Test generation, case-set generation and test runs start as background jobs; cancelling reads the flag from the database, so it works across invocations.

## Claude (AgentCore runner)

How it works: with `PORTAL_CLAUDE_AGENTCORE_RUNTIME_ARN` set (deploy context `claudeRuntimeArn`), a Claude Code session whose credential is an Anthropic API key or a Claude subscription token runs on the `agent-runner` AgentCore runtime (stack `AgentPortalSpikeA`) instead of a local process. The portal sends the credential in the request (`auth`), the runner streams events back (`server/agent/claude-agentcore.ts`), and cost/tokens are recorded like a local run. Bedrock credentials keep using the local SDK path. To use it: Credentials > add a Claude credential (API key or subscription token), then start a session with the Claude Code engine.

### "Invalid API key" in the session
- The credential reached Anthropic and was rejected. Re-enter it in Credentials. (The runner never echoes the key.)

### Claude session says a tool "needs approval"
- A cloud run cannot stop and ask for approval mid-run. Without **Trust all tools** only read-only tools (Read, Glob, Grep, LS, WebSearch, WebFetch, TodoWrite) run. Turn on Trust all tools for sessions that must edit files or run commands.

### Claude runs but nothing changes / files missing afterwards
- The agent works inside the AgentCore microVM (`/tmp/agent-sessions/<id>/work`), which is released after about 5 idle minutes. Files it writes there are not copied back to the portal yet; only the text, tool activity and cost come back.

### Changing the runner
- Build from the repo root: `docker buildx build --platform linux/arm64 -f agent-runner/Dockerfile -t <ecr>/agent-portal/agent-runner:<tag> --push .`, set `IMAGE_TAG` in `infra/lib/spike-a-stack.ts`, `cdk deploy AgentPortalSpikeA`.
- Quick check without the portal: `aws bedrock-agentcore invoke-agent-runtime --agent-runtime-arn <arn> --runtime-session-id <33+ chars> --payload fileb://payload.json out.txt`. A fake key should return `Invalid API key`.

## Storage

### Setup wizard Storage step: S3 test fails with 403 / "request failed"
- **Cause:** the wizard's POST was blocked by the CloudFront POST problem above, and the `/api/admin/test-storage` route did not exist.
- **Fix:** route added (`server/storage-test.ts`); the Lambda role gets read/write on the configured bucket (`storageBucket` context).

### Files disappear after a while (uploads, edited session files, output files, generated documents)
- **Cause:** Lambda's disk (`/tmp`) is wiped whenever the instance is recycled.
- **Fix:** with `STORAGE_BACKEND=s3`, files under DATA_DIR are mirrored to the bucket (`server/durable-files.ts`): `persistFile` after writing, `restoreFile` before reading one file, `restoreTree` before listing a session's folders, `forgetFile`/`forgetTree` on delete. Mirrored: vault, knowledge, attachments, doc templates, session files (work and uploads folders, create/edit/upload/rename/delete), output files (their vault copies), generated documents and presentations. The key in the bucket is the path relative to DATA_DIR.
- **Not mirrored on purpose:** git working copies and repository clones (large, can be cloned again) and agent scratch folders (`home`, `.kiro`, `.claude`).
- **Check:** `aws s3 ls s3://<bucket>/data/ --recursive | head`.

## Session chat: duplicate message, endless "Thinking…", history missing after refresh

Three separate causes, all in the web app:

1. **Saved history never appeared after opening a session.** The first transcript fetch in `SessionLive.jsx` set `loadedInitialTranscript` and listed the same value as an effect dependency, so React re-ran the effect and cancelled the fetch that was still in flight. Fix: the effect depends only on the session and project.
2. **A sent message showed twice, and "Thinking…" never cleared.** The temporary bubble was only removed when the saved copy arrived through the live run stream, but user messages are saved as session events and only appear in the transcript. Fix: while a sent message is unconfirmed, the page re-reads the transcript every 2 s and matches the saved copy by text and send time.
3. **The agent's reply did not show until a refresh.** The live channel (AppSync Events) can miss events. `useRunStream` now also re-reads the stored run history every 2.5 s until the run reports it has ended.

Also note: a deploy replaces the Lambda; a run that is in flight at that moment is cut off. Avoid deploying while testing a run.

## Tool packs: pack says "installed" but is gone after refresh (Lambda)

On Lambda the pack folder is `/tmp/data/tools/...`, which disappears when the instance is replaced. The Icon diagrams install now copies the whole folder to S3 (`data/tools/icon-diagrams/`), and the status page and diagram rendering restore it on demand (in parallel; ~3,700 files). `uv` and Kiro CLI installs still cannot work on Lambda (`curl` is not in the image) and report "finished" even when the download failed.

## Repositories: "Failed while resolving deltas (45%)" when adding a repository (cloud)

- **Cause:** "Add repository" cloned the whole repository into Lambda's `/tmp` after the HTTP reply had been sent. Lambda freezes or recycles the instance after replying, which killed git part-way; `/tmp` was also only 512 MB.
- **Fix:** In the cloud (`AWS_LAMBDA_FUNCTION_NAME` set, or `PORTAL_REPO_SYNC_MODE=check`) adding or syncing a repository only runs `git ls-remote --symref` to check access and read the default branch; nothing is cloned on Lambda. The sync runs as a background job (`repo-sync`), and Lambda's `/tmp` is 4 GB.
- **Where the code goes instead:** the session's repositories are cloned inside the agent's AgentCore microVM at the start of each run (`server/agent/runner-repos.ts`, shared by both runners). Git credentials are passed as `GIT_CONFIG_*` http.extraHeader settings, never in a URL or command line. Kiro and Claude runs need git in the runner image (kiro-runner did not have it).
- **Existing repositories in `error`:** click Sync again; they become `ready`.

## Repositories in a session: workspace on the machine, saved to S3

- **How it works:** the runner keeps the session's repositories in a folder on its own disk (`agent-workspace` under the temp folder, `PERSIST_ROOT` in `server/agent/runner-repos.ts`), linked in as `repos/` for the agent. A machine is released after 5 idle minutes, so after each message (and after the "prepare" step) the runner packs `repos/` (tar + gzip, includes anything the agent installed such as `node_modules`) and uploads it to S3; on a fresh machine of the same session it downloads and unpacks that copy before the usual "bring the repository up to date" step (`server/agent/runner-snapshot.ts`). Each portal session has one fixed AgentCore session id (`server/agent/agentcore-session.ts`), and the portal does the prepare step when repositories are attached (`server/agent/repo-prep.ts`).
- **No AWS permissions in the runner:** the portal sends two presigned URLs (`snapshot: { getUrl?, putUrl }`, made in `server/agent/runner-snapshot-access.ts`, valid 2 hours). The runner only accepts https `amazonaws.com` URLs. The object is `data/workspace-snapshots/<workflowId>.tar.gz` in the storage bucket; the portal deletes it with the session, and a bucket rule (`expire-workspace-snapshots`, applied once with `aws s3api put-bucket-lifecycle-configuration`) expires it 14 days after its last save. In local mode (no S3) there is nothing to hand out and the workspace lasts as long as the machine.
- **When it saves:** only if something in `repos/` changed since the last save (git's own `FETCH_HEAD`/index/logs do not count), and not above 3 GB. It runs after the reply has ended; `/ping` reports `HealthyBusy` meanwhile so the machine is not released, and a message that arrives during the save cancels it (the new run saves again when it ends) instead of waiting or getting a 409. `git fetch --depth 1` rewrites `.git/shallow` every time, so that file is ignored when deciding whether anything changed. Failures are logged (`workspace_save_failed`, `workspace_restore_failed`; successes are `workspace_saved`, `workspace_restored`, `workspace_save_skipped`, and `workspace_changed` names the files that triggered a save, in the runtime's CloudWatch log group `/aws/bedrock-agentcore/runtimes/<runtime>-DEFAULT`) and never fail a message: the repositories are simply cloned again.
- **Edits are kept:** a repository the agent has changed (uncommitted edits or commits) is never reset by the refresh step.
- **Replaced approach:** AgentCore session storage mounted at `/mnt/workspace` (1 GB, wiped on every runtime version, mount quirks such as "dubious ownership" and failed cleanups on big repositories) is no longer used and the mount was removed from both runtime stacks. The scoped `safe.directory` handling remains in `runner-repos.ts` and is harmless.
- **A new image does not take effect for a warm session:** a runner machine that is still alive (5 minutes idle limit) keeps running its old image. After deploying a runner image, wait for it to go idle (or use a new session) before testing.
- **Seeing why a clone failed:** the prepare status shows git's exit code or signal, free disk and memory, and the last error lines.
- **Measured on `rhb.backend.shared` (1.9 GB working tree, mostly `lambda/`) plus the frontend repo:** first save about 46 s in the background (884 MiB); restore on a fresh machine 17-20 s, about the same as a clone (24 s), so the benefit is that edits and installed dependencies survive, not clone speed.

## Integrations: remote MCP servers in a session

The Integrations page has two parts. **Connected services** is an overview of sign-ins the portal already has (Jira from Tickets, Git hosts from Connections, model sign-ins from Credentials) with links to where each is managed. **MCP servers** are the ones added on that page.

- **What is stored:** per project, in `mcp_integrations` (type `http`), the whole config (URL, secret headers, allow-writes, personal flag, last test result) encrypted in `config_enc`. The browser only ever gets the URL, the header *names*, the flags and the last test result; header values are write-only (an empty value on edit keeps the stored one).
- **Per session:** the session's Context tab has an Integrations section. "Project default" gives the session every integration that is On; "Choose for this session" limits it to the ticked ones (none ticked = no MCP tools). Stored in the session's `integrations` field (`[]` = default, `{"ids":[...]}` = chosen), changed with PATCH `integrationIds` (null = default). It applies from the next message.
- **What a session gets:** when a run starts on AgentCore, `buildRunnerMcpServers` (server/agent/runner-integrations.ts) decrypts every enabled `http` integration of the project (plus the person's own "Only me" ones) and sends `mcpServers` in the invoke payload. Attached per project, not per session: turn an integration Off to stop sessions getting it.
- **How the runner uses it:** it does not give the server to Claude or Kiro directly. It starts `dist/mcp-proxy.mjs` (server/agent/runner-mcp.ts) as a local stdio MCP server per integration, with the spec in the env var `MCP_PROXY_SPEC`. The proxy sends the secret headers, hides tools that are not read-only (a tool says `readOnlyHint: true`, or has no hint and its name starts with get/list/search/read/describe/fetch/query/find/view/show/lookup/count) and refuses calls to them, unless "Allow writes" is on. Tools show up as `mcp__<name>__<tool>` (Claude) or under the server name (Kiro).
- **Test:** "Save and test" and "Test" connect from the portal Lambda over streamable HTTP (initialize, tools/list), after an SSRF check (private and metadata addresses refused), and show "N of M tools offered". The Lambda must be able to reach the server on the internet.
- **Not supported yet:** command (stdio) servers, Atlassian sign-in as an MCP server, Google Drive, AWS read-only tools. Older entries of those types are listed but are not given to sessions.
- **A server that needs OAuth** (browser sign-in) cannot be added with a header; use one that accepts a token or API key header.
- **"Needs attention" after saving:** the message says why (HTTP status, "did not answer in time", "SSRF blocked"). A runner image older than this feature ignores `mcpServers` silently, so after deploying wait for warm machines to go idle before testing.
- **Kiro says an MCP tool failed with a permission error ("missing field outcome"):** kiro-cli asks `session/request_permission` before it runs an MCP tool and wants the answer as `{ outcome: { outcome: 'selected', optionId } }`. The runner used to answer with a bare `optionId`, which built-in tools never needed. Fixed in kiro-runner `run.ts`; a machine on an older image still shows it until it is released.
- **A session ignores new messages:** check `iteration_count` against `max_iterations` (PATCH `maxIterations` raises it); a session that hit its limit shows `stop_reason: max_iterations` and starts no run.

## Session says it has no browser (cloud)

- **Cause:** the AgentCore Browser tools are opt-in per deployment. Without `-c agentcoreBrowser=true` the portal Lambda has no `PORTAL_AGENTCORE_BROWSER=1`, the runner is never told to start the browser, and the agent answers that it cannot browse. Every `cdk deploy AgentPortalCloud` must repeat this context value, or the setting is dropped again.
- **Check:** `aws lambda get-function-configuration --function-name agent-portal --query Environment.Variables.PORTAL_AGENTCORE_BROWSER` should print `1`. The runtime roles already allow the browser calls.
- **Cost:** a browser session only bills while open; it starts on the agent's first browser tool call.
- **Browser tab stays empty although the agent browses:** the tab shows what the runner sends as `browser-navigate` / `browser-screenshot` events. After `goto`, `click` and `type` the browser tools take a small JPEG (at most 250 000 base64 characters, never shown to the model) and hand it to the live view: in the Claude runner straight to the event stream, in the Kiro runner through a folder (`BROWSER_LIVE_DIR`) that the runner empties every 0.5 s, because the browser MCP is a child of kiro-cli. The tab is not interactive for cloud runs (view only) and shows the latest picture, so it is small in the narrow side panel; widen the panel or use the pop-out button.

## Message appears in the chat but no run starts

- **Cause (fixed):** the composer only called `/start` when its copy of the session status said "not running". Right after a run ended that copy could still say "running", so the message was saved and never answered; `/start` errors (for example the iteration limit) were also swallowed. Now it always calls `/start` (the server ignores it when a run is going) and shows the reason when the start fails.

## Browser tab: live video of the agent's cloud browser (AgentCore Live View)

**What it is.** In the cloud portal the Browser tab streams the agent's AgentCore browser as real video (AWS DCV) and, with **Remote** switched on, lets you use the mouse and keyboard in it. The stream goes from AWS straight to your browser; the portal only signs a 5-minute address.

**What it needs**
- `-c agentcoreBrowser=true` on every `cdk deploy AgentPortalCloud` (otherwise the agent has no browser at all).
- Both runner images from this change or later (they announce the browser session id with a `browser-session` event).
- The Lambda role policy `bedrock-agentcore:ConnectBrowserLiveViewStream`, `UpdateBrowserStream`, `GetBrowserSession` (in `infra/lib/portal-stack.ts`).
- The viewer is vendored in `web/vendor/agentcore-live-view/` (from `bedrock-agentcore` 0.4.6, Apache-2.0; it bundles the NICE DCV web client with its own licence). The DCV worker files are copied to `dist/web/nice-dcv-web-client-sdk/` by `scripts/build.mjs`.

**How it behaves**
- `GET /api/workflows/:id/browser/live-view` returns `{ available, url, sessionId, width, height }`. It is only available while a run is active and the agent has opened a browser; the browser closes when the run ends, so the tab goes back to "Not running".
- **Remote on** calls `POST /api/workflows/:id/browser/live-view/control` (project editor), which uses AgentCore `UpdateBrowserStream` to pause the agent's control. **Remote off** hands control back. The switch resets to off for each new browser session.
- Viewport is fixed at 1280x800; the component must be given the same size or the picture is cropped.

- The older picture-after-each-action feed (`browser-screenshot` events) is still emitted and stored; it is only shown when no live stream is available.

If `uv` fails with a download error, the image running is older than tag `br-202611056`/`br-202611058`: warm AgentCore machines keep the old image for about 5 minutes after a deploy.

## Tests: choosing the AI credential and model (2026-11-04)

- Generate with AI has a Credential list (Claude and Kiro credentials of the signed-in person) and a Model list. With no credential of their own the portal's provider is used; if that is unset (demo) and the person has no credential, generation says so.
- A Kiro credential sends the prompt through the Kiro runner. Kiro is an agent and may answer in prose, so the prompt ends with an instruction to give only the output, and generation retries once when the reply has no JSON array. The error now shows what the model said: `Model output did not contain a JSON array. The model said: "..."`.
- The model is passed to kiro-cli with ACP `session/set_model`; if the model cannot be set the run goes on with Kiro's default and a status line says "Could not use model ...". Sessions use the same path. A Tests-page generation has no run feed, so to check the model, start a session with a specific model and look for the status line `Model: <id>`.

## DynamoDB run events: read enough of them

`listWorkflowRunEventsByType` reads only the first `limit` events of a run (oldest first) and then filters by type. For rare types such as `browser-session` or `check-result` use a large limit (500), or they are missed in long runs. This was why Live View vanished in later runs.

## Loop sessions and loop triggers (port branch)

**Loop session.** A session created with `loop: { stopRules, checks }` goes from run to run by itself. After each run `afterRun` (server/workflows/loop.ts) records the iteration and either starts the next run or stops with a reason: failures in a row, the agent reporting blocked or done, no progress over several iterations, the iteration limit, the budget or the time limit. State is the `loop_state` JSON on the session. Checks (`{ step, cmd }`) run inside the runner after each iteration, in a credential-free environment, are guarded like agent commands, and their result goes into the next prompt (`check-result` event). A check the guard refuses makes the create call return 400.

**Triggers** (`server/loop-triggers.ts`, loop specs page).
- `cron` (5 fields, UTC) and `interval` (every N minutes, at least 5) specs are started by the `loop-triggers` job: an EventBridge Scheduler schedule `agent-portal-loop-triggers`, `rate(1 minute)`, calling `/internal/events`; locally a timer. A tick that is a minute late still fires once.
- `webhook` specs: `POST /api/hooks/loop-specs/<specId>` with header `x-portal-signature: sha256=<HMAC-SHA256 of the raw body, key = the spec's secret>` (`x-hub-signature-256` is accepted too). The secret is shown once on create (or from `POST .../loop-specs/<id>/webhook-secret`) and is never returned again. Wrong signature and unknown spec both return 401. Body values become `{{a.b}}` in the goal template.
- A triggered session runs as the person who last saved the trigger (`runAs`) and only while they are still project editor or owner; "trust all tools" is always off, so a tool needing approval waits in the inbox; it does not start while the spec's previous session is still running (409) and starts at most `maxPerHour` (default 3) times an hour (429). "Run now" by a person skips the last two.
- `github` and `jira` trigger types are accepted but do not start sessions yet; use a webhook.

### Claude Code session text appears all at once after a long wait
- **Symptom:** a Claude Code session on the AgentCore runner shows nothing while the model is working, then a whole reply (or several) appears at once. Kiro sessions were fine.
- **Cause:** `agent-runner/src/run.ts` only forwarded the SDK's finished `assistant` messages, so text reached the portal once per message.
- **Fix:** the runner now sets `includePartialMessages: true` and forwards each `text_delta` as `assistant-text` with `stream: true` (and `thinking_delta` as `thought`); the finished message's text is skipped when it was already streamed, and `server/claude-agentcore.ts` passes `stream` through so the viewer joins the pieces. Needs runner image `br-202611058` (stack `AgentPortalSpikeA`) and a portal deploy. A warm runner machine keeps the old image until it goes idle (5 minutes), so use a new session to test.

### Every Kiro chat message restarted kiro-cli
- **Symptom:** each message in a Kiro session showed "kiro-cli ACP starting…" again and was slow to begin; the repositories were put in place again each time.
- **Cause:** `kiro-runner/src/run.ts` started `kiro-cli acp`, created an ACP session and closed everything at the end of every message.
- **Fix:** after a run that went well, the runner keeps the kiro-cli process and its ACP session (`warm`), and the next message is only a `session/prompt` ("Continuing in the same kiro-cli session." in the status lines). A fresh start happens when the machine is new (idle 5 minutes), the repositories (name, address, branch), integrations (name, address) or browser setting changed (tokens inside them are ignored, they change every message), the last run failed or timed out, or the process is older than 12 minutes in a browser session (a cloud browser session lasts 15 minutes; the browser-session event is announced again on each message so the live view still finds it). Needs runner image `br-2026110512` (stack `AgentPortalSpikeB`); a warm machine keeps the old image until idle.

### Too much space between a page's tabs and its first button
- **Symptom:** about 50px of empty space under the tab bar on the Tests page (and 30 to 40px on several others).
- **Cause:** `.page` is a grid with an 18px gap, and the tab bar (20px margin below), the tab panel (16px padding above) and some headers (inline `marginBottom: 16`) each added their own space on top of it.

### AWS accounts for agents (per project)
- **Where:** Workspaces › AWS. The account marked "agents use this" is the project's default; its keys are stored encrypted (`server/project-aws.ts`, table `aws_accounts`, setting `aws.default.<projectId>`).
- **How agents get it:** when a cloud (AgentCore) session starts, the portal decrypts the keys and sends them in the invoke payload as `awsEnv` (only `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION`, `AWS_DEFAULT_REGION`; the runners drop anything else). The Kiro runner puts them in kiro-cli's environment and removes the machine's own role variables, so the agent can only act as that account; the Claude runner does the same when the session uses an Anthropic credential (with Bedrock the machine's role is still needed, so the variables are not applied). Changing the account restarts a warm kiro-cli on the next message.
- **Old tab:** Agent setup no longer has an AWS (~/.aws) tab: those files only reached local runs, never AgentCore sessions. Needs runner images `br-2026110514`.

### Create: "No .drawio file found in run folder", documents that cannot be downloaded
- **Symptom:** a diagram failed in 4 seconds with "No .drawio file found in run folder"; a document showed "Ready" but "Download" said the file was not found; the dialogs never asked which model or which files to use.
- **Cause 1:** diagrams, documents and presentations all started their run on the simulated `demo` engine (no credential, no model), which writes no real files. **Cause 2:** on the DynamoDB backend `getVersionById` for generated documents was a stub that always returned nothing, so every download said "Version not found". **Cause 3:** the Word file was never built from the Markdown. **Cause 4:** the document dialog sent `sources: {}`, so no repository or project document ever reached the agent, and files staged in the portal's run folder (attachments) were never sent to the AgentCore runner.
- **Fix:** `server/create-ai.ts` picks the engine, sign-in and model (the one chosen in the dialog, else the person's default sign-in; a cloud portal with no sign-in says so instead of falling back to demo). The three dialogs have the credential/model picker, and the document dialog has a "What the agent reads" section (repositories, Knowledge documents, attachments). Repositories go to the runner as for a session; staged files (`attachments/`, `docs/md/`) travel in the invoke payload as `inputFiles` and are written into the work folder by the runner. Versions are read with `getLatestVersion`; the Word file is built with `buildDocx`; a run that leaves no Markdown marks the document failed. Needs runner images `br-2026110515`.
- **Old records:** documents and diagrams made before this fix came from the demo engine; use Refresh (or Delete) on them.
- **Still true:** the agent can only read a repository the portal can clone. A Git connection that uses temporary AWS keys stops working when they expire (the repository shows `error` with a 403 from CodeCommit): update the keys under Connect › Git connections.

### Knowledge Ask: how it answers
- **Before:** Search and Ask were keyword-only. Ask pasted the first 500 characters of the top 5 documents under "Based on the project documents".
- **Now:** the keyword index still finds the documents (`searchDocs`), but `server/knowledge-answer.ts` reads their Markdown, cuts it into passages under their headings, and ranks the passages by the question's words. Search shows the matching lines (with the heading). Ask gives the best 6 passages, numbered, to a model through `callTextModel` (the credential and model chosen on the Ask tab, else the person's default sign-in; a Kiro sign-in runs as a short session, so the first answer takes about 15 to 20 seconds) with instructions to answer only from them and cite `[n]`. The answer lists its sources, marking the cited ones.
- **No sign-in or model failure:** Ask falls back to returning the matching passages themselves, with a note saying why. Matching is still by exact words, so a question with none of the document's words finds nothing.

### Knowledge search setup (keywords, meaning-based index, AWS Knowledge Base)
- **Where:** Knowledge › "Search setup" (a popup). The choice is per project (setting `knowledge.search.<projectId>`); Search and Ask both use it, and say which backend answered. A backend that fails falls back to keywords with a note.
- **Meaning (portal index):** each passage is embedded with Bedrock `cohere.embed-multilingual-v3` (1024 numbers, unit length) and stored per document at `projects/<slug>/docs/vec/<docId>.json` (mirrored to S3); a question is embedded the same way and the closest passages win, merged with the keyword ranking (reciprocal-rank fusion). Uploads are indexed automatically once chosen; "Index documents" does the existing ones. The portal's Lambda role has `bedrock:InvokeModel` on that model only. Code: `server/knowledge-embeddings.ts`, `server/knowledge-search.ts`.
- **AWS Knowledge Base (one for all projects):** the stack always creates the idle, free prerequisites: an S3 Vectors bucket and index (1024 dimensions, cosine) and the service role (env `PORTAL_KB_ROLE_ARN`, `PORTAL_KB_INDEX_ARN`, `PORTAL_KB_EMBED_MODEL_ARN`, `PORTAL_KB_BUCKET_ARN`). An admin presses "Create the shared Knowledge Base" in Knowledge › Search setup; the portal then creates the Knowledge Base (Cohere Embed Multilingual v3, S3 Vectors store) and one data source over `data/kb/` of the storage bucket, and remembers them in the setting `knowledge.kb`. Its Lambda role may create, sync, query and delete Knowledge Bases of this account and region, and pass only the one service role to Bedrock. The portal copies each ready document's Markdown to `kb/<slug>/<docId>.md` with `<docId>.md.metadata.json` beside it (`{"metadataAttributes":{"projectId":"<project id>"}}`); a search passes the filter `equals projectId = <project id>`, applied before ranking, so projects never see or crowd out each other's documents (checked with two labelled test documents; the portal also drops hits outside the project's own `kb/<slug>/` folder). "Copy documents and sync" (re)writes copies and labels and starts an ingestion job; uploads and deletes start one while the Knowledge Base is chosen. An admin can remove the Knowledge Base from the same popup; documents are untouched. No deploy flag is needed (an earlier version used `-c knowledgeBase=true`; that flag is gone).
- **Cost:** embeddings are fractions of a cent per document; the Knowledge Base on S3 Vectors is pay-per-use (storage, requests, ingestion embeddings) with no fixed monthly minimum.

### Knowledge: reading a document with the referred passage highlighted
- Search results, Ask sources and the document names in the Documents list open a viewer (`KnowledgeDocViewer`). It shows the text the portal converted from the file (Markdown, from `GET /api/projects/:id/knowledge/docs/:docId/content`, first 400,000 characters), not the original file. The passage a result or answer pointed to is sent along (`passage`) and the viewer highlights the blocks of the document that contain it, or are contained in it, or overlap it at an end (a Knowledge Base chunk may start or stop mid-paragraph), then scrolls to the first one. When the passage cannot be located the viewer says so and highlights nothing.

### Vault: folders can be selected and deleted
- Vault folders are not stored anywhere: a folder is the `folder` path on the files inside it. So ticking a folder (checkbox on its row, or "select all folders") means every file at any depth below it, and deleting it deletes those files. The bulk bar counts files and folders together; "Move to…" shows only when files alone are ticked. Each folder row also has its own delete button. The confirmation says how many folders and files will go.
- `POST /api/projects/:id/vault/delete` takes `skipOthers: true` (sent for folders): files uploaded by someone else, or already gone, are skipped and counted instead of refusing the whole request, and the S3 copies of deleted files are now removed too (they were left behind before). Batches are 500 files.
